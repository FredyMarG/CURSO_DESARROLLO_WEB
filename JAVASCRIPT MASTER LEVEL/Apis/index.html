Fundamento 01

¿Qué es una API? Interfaz de Código vs. Interfaz de Usuario

Una API (Application Programming Interface) es un conjunto de reglas y definiciones que permite que diferentes aplicaciones de software se comuniquen entre sí:

El Puente entre Sistemas

Abstracción y Seguridad: Actúa como un intermediario que permite a tu código solicitar datos o servicios de un servidor externo sin necesidad de conocer cómo está programado ni cómo gestiona su base de datos interna.

Automatización Pura: Permite el intercambio directo de información estructurada entre servidores, navegadores web y aplicaciones móviles en milisegundos.

💡 Diferencia Clave: Mientras la UI conecta a un humano con una máquina, la API conecta máquina con máquina mediante código.

Interfaz de Usuario (UI)

  • Diseñada para la interacción humana visual.
  • Usa botones, menús, formularios y pantallas.
  • Consume datos ya procesados y listos para leer.

Interfaz de Código (API)

  • Diseñada para la comunicación entre programas.
  • Usa URLs (Endpoints), métodos HTTP y cabeceras.
  • Intercambia datos estructurados en formato JSON.
peticion_basica_fetch.js 
// Solicitamos los datos del usuario 42 al Endpoint de la API:
fetch('https://api.ejemplo.com/v1/usuarios/42')
  .then(response => response.json())
  .then(data => console.log(data));

Fundamento 02

Sintaxis Básica y Anatomía de una Petición HTTP

La comunicación con una API web se realiza a través del protocolo HTTP combinando 4 componentes fundamentales:

Estructura HTTP

Los 4 Componentes Clave

Endpoint + Method + Headers + Body
  • 1. Endpoint (Ruta): La URL única que identifica el recurso (ej. /v1/usuarios/42).
  • 2. Método HTTP (Verbo): Define la acción a ejecutar (GET, POST, PUT, DELETE).
  • 3. Headers (Cabeceras): Metadatos clave-valor (tipo de contenido, tokens de autenticación).
  • 4. Body (Cuerpo): Datos estructurados enviados al servidor (en POST, PUT, PATCH).
🔗
Identificación de Recursos: En REST, cada URL representa un sustantivo claro (ej. /libros, /productos).

Acciones del Protocolo

Métodos (Verbos) HTTP

GET, POST, PUT / PATCH, DELETE

El mismo Endpoint (por ejemplo, /usuarios) puede realizar acciones completamente distintas dependiendo del verbo HTTP utilizado en la petición:

⚡
Convención Estándar: GET solo lee datos (sin Body); POST crea recursos enviando un Body JSON.
fetch(endpoint, { method: "POST | GET | PUT | DELETE", headers: {...}, body: JSON })

Método HTTP Propósito / Acción CRUD ¿Requiere Body? Ejemplo de Endpoint
GET Solicitar u obtener datos de un recurso ❌ No lleva Body GET /v1/usuarios/42
POST Enviar información para crear un nuevo recurso ✅ Sí (JSON en Body) POST /v1/usuarios
PUT / PATCH Actualizar un recurso existente (total o parcial) ✅ Sí (JSON en Body) PUT /v1/usuarios/42
DELETE Eliminar un recurso específico del servidor ❌ Generalmente No DELETE /v1/usuarios/42

Formato Estándar JSON y Diagrama de Flujo de Decisión HTTP

Domina cómo se serializan y parsean los datos en formato JSON y cómo bifurcar el flujo según el código de estado HTTP (2xx vs. 4xx/5xx):

5.1 JSON (JavaScript Object Notation)

El lenguaje universal de intercambio de datos en la Web

Es una representación textual ligera de los objetos de JavaScript. Al enviar datos al servidor los convertimos a texto con JSON.stringify(obj), y al recibirlos los transformamos en un objeto nativo manipulable mediante await response.json() o JSON.parse().

5.2 Diagrama de Flujo de Decisión por Código de Estado

¿Código 2xx (Éxito) o Código 4xx / 5xx (Error)?

Cuando el cliente envía una petición HTTP, el servidor responde con un código numérico: 2xx (ej. 200 OK, 201 Created) indica éxito y procede a procesar el JSON; 4xx (error del cliente, ej. 404 Not Found) o 5xx (fallo del servidor, ej. 500) debe desviarse al bloque catch para mostrar una alerta controlada en pantalla.

5.3 ¿Por qué es obligatorio verificar 'response.ok'?

Fetch NO lanza excepción automática en errores 404 o 500

En JavaScript, fetch() solo rechaza su promesa automáticamente si falla la red física (sin internet). Si el servidor devuelve un error 404 o 500, debemos verificar explícitamente if (!response.ok) throw new Error(...) antes de transformar o mutar nuestros datos.

Seguridad y Estabilidad

Buenas Prácticas y Errores Comunes al Consumir APIs

Evita vulnerabilidades de seguridad y fallos silenciosos aplicando los estándares profesionales de la industria:

❌ ERROR GRAVE: CREDENCIALES EXPUESTAS

Exponer API Keys en el Front-end

Escribir claves privadas en el código del navegador permite que cualquier usuario las robe desde la pestaña Network de DevTools. Usa un servidor propio como intermediario.

fetch("https://api.com?key=12345_SECRET"); // ❌ Peligro
❌ ERROR COMÚN: LECTURA SÍNCRONA

Ignorar la Asincronía de la Red

Las llamadas de red toman tiempo. Leer propiedades directamente de fetch() sin esperar con await o .then() devolverá undefined sobre una Promesa pendiente.

const d = fetch(url); console.log(d.nombre); // ❌ undefined
✅ BUENA PRÁCTICA: VALIDAR ESTADO

Verificar siempre response.ok

Comprueba el estado booleano response.ok (true para códigos 200-299) antes de ejecutar response.json() para capturar respuestas 404 o 500 de forma segura.

if (!response.ok) throw new Error(response.status); // ✅
✅ BUENA PRÁCTICA: ARCHIVOS .ENV

Usar Variables de Entorno

Almacena siempre las credenciales y API Keys en archivos de configuración .env fuera del control de versiones para evitar filtraciones en repositorios públicos.

const apiKey = process.env.REACT_APP_MI_API_KEY; // ✅
Implementación Práctica

Consumo Asíncrono con async/await: Peticiones GET y POST

Observa cómo estructurar peticiones de lectura (GET) y creación (POST) con cabeceras y validación de errores:

1. Petición GET con async/await y Validación

Esperamos la resolución de red con await, verificamos response.ok y transformamos el cuerpo a JSON de forma segura: 

async function conseguirDatos() {
  const res = await fetch("https://api.ejemplo.com/perfil");
  if (!res.ok) throw new Error("Error HTTP: " + res.status);
  return await res.json();
}

Nivel 2 — Semi Senior

Optimización con async/await y Validación

Corrige y optimiza la función conseguirDatos() agregando el manejo correcto de asincronía (async/await) y la validación de errores (response.ok) antes de transformar el cuerpo a JSON. 

async function conseguirDatos() {
    try {
        const respuesta = await fetch("https://api.ejemplo.com/perfil");
        if (!respuesta.ok) {
            throw new Error(`Error HTTP: ${respuesta.status}`);
        }
        const usuario = await respuesta.json();
        return usuario;
    } catch (error) {
        console.error("Fallo al obtener perfil:", error.message);
    }
}
Nivel 3 — Avanzado

Petición POST con Headers y Body JSON

Escribe una función con fetch que envíe una petición POST a https://api.ficticia.com/productos con el objeto JSON { nombre: "Teclado Mecánico", precio: 85 } y la cabecera Content-Type: application/json. 

async function crearProducto() {
    const respuesta = await fetch("https://api.ficticia.com/productos", {
        method: "POST",
        headers: {
            "Content-Type": "application/json"
        },
        body: JSON.stringify({
            nombre: "Teclado Mecánico",
            precio: 85
        })
    });
    if (!respuesta.ok) throw new Error(`Estado: ${respuesta.status}`);
    return await respuesta.json();
}
