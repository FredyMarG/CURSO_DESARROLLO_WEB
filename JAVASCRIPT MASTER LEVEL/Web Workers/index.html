Arquitectura de Navegador

1. ¿Por qué son necesarios los Web Workers?

JavaScript es un lenguaje de un solo hilo: si una operación bloquea ese hilo, la interfaz entera deja de responder.

⚠️ Todo en el Main Thread

Bloqueo Total de la Interfaz

Si ejecutas un bucle de 2 mil millones de iteraciones en main.js:

  • ❌ Los botones dejan de responder a los clics.
  • ❌ Las animaciones CSS y el scroll se congelan.
  • ❌ El navegador muestra el aviso de "La página no responde".
✅ Con Dedicated Worker

Ejecución Paralela Fluida

Delegar la carga pesada a un hilo secundario mantiene el navegador ágil:

  • ✔️ El usuario sigue navegando y haciendo clic sin interrupciones.
  • ✔️ El cálculo corre en paralelo en otro núcleo de la CPU.
  • ✔️ Al finalizar, el resultado llega limpio mediante evento.
Ecosistema Web

2. Tipos de Web Workers

Cada variante cumple un rol distinto según el alcance de la tarea y el ciclo de vida de la pestaña.

⚙️

Dedicated Worker

new Worker("worker.js")

El más común. Pertenece exclusivamente al script/pestaña que lo creó y muere automáticamente al cerrarla.

🌐

Service Worker

navigator.serviceWorker

Proxy de red programable: intercepta peticiones fetch, gestiona caché offline (PWAs) y notificaciones Push.

🧱

Abstract Worker

onerror (Interfaz Base)

No se instancia directamente; es la interfaz base de la que heredan Worker y SharedWorker.

Instanciación & Configuración

3. El Constructor `Worker()` y su parámetro `options`

Se instancia pasando la ruta del archivo separado y un objeto opcional con tres propiedades clave.

📦

Sintaxis con Opciones

const miWorker = new Worker("worker.js", {
  type: "module",
  credentials: "same-origin",
  name: "procesador-datos"
});
⚙️

Propiedades de `options`

type "classic" (defecto) o "module" para usar import/export.
credentials Envío de cookies/cabeceras en módulos: "omit", "same-origin" o "include".
name Nombre legible en DevTools, accesible dentro como self.name.
Paso de Mensajes

4. Comunicación Bidireccional: `postMessage()` y `onmessage`

Al vivir en entornos de memoria aislados, los hilos se comunican enviando copias mediante el Structured Clone Algorithm.

En main.js (Hilo Principal)

Enviar y Escuchar Respuesta

const worker = new Worker("worker.js");

// 1. Enviamos carga de trabajo
worker.postMessage({ accion: "calcular", n: 500000 });

// 2. Recibimos respuesta en e.data
worker.onmessage = (e) => {
  console.log("Resultado:", e.data);
};
En worker.js (Hilo Secundario)

Procesar y Devolver

// 1. Escuchamos mensajes del padre
self.onmessage = (e) => {
  const { accion, n } = e.data;
  if (accion === "calcular") {
    const res = n * 2;
    // 2. Devolvemos resultado
    self.postMessage(res);
  }
};
Gestión de Memoria

5. Finalización del Ciclo de Vida: `terminate()` y `self.close()`

Cada worker consume RAM y CPU del sistema operativo; detenerlos cuando terminan libera recursos de inmediato.

🛑

Desde main.js: `worker.terminate()`

Detiene abruptamente al worker sin esperar a que termine su tarea actual. No puede reutilizarse después.

miWorker.terminate();
console.log("Worker destruido desde el hilo principal.");
🔌

Desde worker.js: `self.close()`

El propio trabajador cierra su hilo tras enviar su último resultado al hilo principal.

self.postMessage("Tarea finalizada");
self.close(); // Se cierra a sí mismo
Seguridad & Entorno

6. Política de Origen Cruzado (*Same-Origin*) y Limitaciones

Reglas estrictas de seguridad y aislamiento que debes tener presentes al trabajar con hilos secundarios.

🔒

Mismo Origen

worker.js debe provenir del mismo protocolo, dominio y puerto. URLs externas lanzan SecurityError.

🌐

Bloqueo en `file://`

Abrir index.html directamente desde disco bloquea la carga del worker; usa siempre localhost o Live Server.

🧩

Sin DOM ni `window`

Dentro del worker no existen document, window ni parent. Solo procesa datos y responde vía postMessage().

7. Analogías y Buenas Prácticas

Comprende la separación de hilos y evita errores habituales en producción.

👨‍🍳

El Chef y el Ayudante de Cocina

El Chef (Main Thread) atiende a los clientes en la barra sin parar. Cuando llega un pedido de picar 50kg de cebolla, lo envía por la ventanilla (postMessage) al Ayudante (Worker) en la cocina trasera.

🛡️

Reglas de Oro en Producción

Registra siempre worker.onerror, usa Transferable Objects (ArrayBuffer) para datos gigantes sin copiar memoria, y llama a terminate() al concluir tareas puntuales.

9. Proyecto Integrador: `main.js` + `worker.js`

Estructura limpia con manejo de errores (`onerror`) y cancelación inmediata (`terminate()`).

main.js

Hilo Principal

const w = new Worker("worker.js", { name: "calculo" });
w.postMessage({ iteraciones: 2_000_000_000 });
w.onmessage = (e) => {
  console.log("Resultado:", e.data);
  w.terminate();
};
w.onerror = (err) => console.error(err.message);
worker.js

Hilo Secundario

self.onmessage = (e) => {
  const { iteraciones } = e.data;
  let suma = 0;
  for (let i = 0; i < iteraciones; i++) {
    suma += i;
  }
  self.postMessage(suma);
};

11. Transferable Objects, Blob Workers y Cheatsheet

Transfiere memoria binaria en ~0 ms sin copiarla, crea workers en línea y depura errores.

🚀

Transferable Objects

const buf = new ArrayBuffer(32 * 1024 * 1024);
worker.postMessage(buf, [buf]);
// buf.byteLength === 0 en el emisor

Cede la propiedad de grandes bloques de memoria sin duplicar RAM.

🧩

Inline Blob Worker

const blob = new Blob([code], { type: 'text/javascript' });
const w = new Worker(URL.createObjectURL(blob));

Útil para librerías autocontenidas sin archivos externos.

📋

Cheatsheet Rápido

postMessage() / onmessage (e.data)
worker.terminate() / self.close()
worker.onerror & messageerror

Sin acceso a document ni window dentro del hilo secundario.
